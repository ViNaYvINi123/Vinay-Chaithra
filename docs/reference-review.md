# Reference-product comparison

## Scope of this comparison

The comparison below uses the feature descriptions in the supplied product brief: VisualGo is framed there as problem-driven exploration with a customizable playground; VisuAlgo is framed there as a broad collection of algorithm/data-structure visualizations. This is a design comparison, **not** a claim of a fresh source-code audit, current feature verification, or partnership with either project. No reference code, brand assets, or company content was copied into this repository.

## Product-level takeaways

| Reference direction (as described in the brief) | Useful product idea | What this academy implements | Remaining gap |
| --- | --- | --- | --- |
| VisualGo-style problem-first learning | Put a concrete prompt and editable playground next to each other. | Each day has an exercise and interview prompt; a learner can load a weekly runnable example into the Java-syntax editor. | The full 60-day prompt set is not backed by a unique, runnable solution or automatic judge for every prompt. Several collection/graph prompts are conceptual because the interpreter does not implement the Java Collections API. |
| VisuAlgo-style visual algorithm exploration | Make algorithm state visible while the learner advances through a procedure. | Recorded trace events drive source highlighting, console output, stack/heap snapshots, and a one-dimensional array view. | This is not a broad standalone library of specialized, polished visualizers for every algorithm. The current array panel displays synchronized indexed slots; there are no purpose-built sorting-bar, heap, hash-table, queue, or graph-canvas views yet. |
| Hands-on stepping | Let the learner pause, inspect, and replay a state change. | Run records a deterministic trace; next/previous/play/pause replay it, with breakpoints and explicit resource limits. | The trace is generated by a constrained interpreter, not by a JVM debugger or instruction-level stepping. |

## Deliberate differentiator and honest boundary

The implementation's central idea is a single event log that links executable subset source to both algorithm state and a conceptual memory model. Stable IDs and visible references help explain aliasing and object graphs. They are teaching labels, not actual Java addresses or a physical heap dump. The interface says this directly, and unsupported language/library features fail explicitly.

The current project is a vertical slice, not feature parity with mature visualization collections. Next sensible extensions are: a verified JDK-backed execution option; more grammar plus differential tests; purpose-built, synchronized visualizers for hash tables, stacks/queues, sorting, heaps, and graph traversals; and richer executable exercises. Each extension should preserve the same trace source of truth and add evidence rather than simulated compiler output.
